# 미션 요청 멱등성

## API 사용

```http
POST /ec/v1/{gameKey}/events/{eventKey}/actions/{actionId}
Content-Type: application/json

{"externalUserId":"external-user","requestId":"mission-request-001"}
```

- 클라이언트가 한 번의 논리적 미션 실행에 고유한 requestId를 발급한다. 타임아웃 등으로 재전송할 때에는 같은 ID를 사용한다.
- 새 실행에는 새 ID를 사용한다. 새 ID라도 NONE/DAILY 같은 기존 반복 정책은 적용된다.
- requestId는 선택 필드다. 없거나 null이면 기존 방식으로 실행하며 요청 단위 멱등성은 제공하지 않는다.
- ID는 공백만으로 구성되면 안 되며 최대 128자다. 잘못된 ID는 HTTP 400 / INVALID_ACTION_REQUEST다.
- 현재 MISSION만 지원한다. REWARD에 requestId를 보내면 보장 없는 처리를 조용히 수행하지 않고 HTTP 400을 반환한다.

## 처리 흐름

이벤트·사용자·Action 확인 → User Lock → 저장된 결과 조회 → 미처리 요청이면 기존 검증 후 트랜잭션 실행.

트랜잭션 안에서 최신 실행 결과를 다시 확인하고, 없으면 미션 진행·완료 기록 + 포인트 적립 + 실행 결과 기록을 함께 저장한다.
`{gameKey}_{eventKey}_missionExecution` 컬렉션의 `(userId, actionId, requestId)` 복합 Unique Index가 중복 결과 기록을 차단한다.
서로 다른 게임/이벤트/사용자/미션에서는 같은 requestId 문자열을 사용할 수 있다.

- 같은 ID의 재전송은 최초에 저장한 결과를 반환한다. 진행도와 포인트를 다시 변경하지 않는다.
- 반환하는 points는 최초 실행 당시의 스냅샷이다. 나중에 변경된 현재 잔액으로 대체하지 않는다.
- PROGRESS 결과도 기록하므로 중복 요청으로 진행도가 두 번 증가하지 않는다.
- 결과 기록까지 저장한 뒤 실패해도 전체 롤백하므로 같은 ID로 재실행할 수 있다.
- 커밋 성공 후 응답을 잃은 경우에도 같은 ID로 재전송하면 DB에 저장된 결과를 찾을 수 있다.
- 이미 저장된 결과는 이벤트 종료/비활성화 뒤에도 반환한다. 새 ID의 실행은 이벤트 상태·기간 검증을 통과해야 한다. 이벤트/사용자/Action 자체가 삭제된 경우까지 재반환하는 기능은 아니다.
- 결과 기록 저장이 중복 키로 실패한 요청은 트랜잭션 롤백 후 먼저 저장된 결과를 조회한다. 다른 DB 오류를 무조건 정상 결과로 바꾸지 않는다.

## 검증

실제 MongoDB의 임시 DB에서 검증한다. 테스트에 따라 JVM User Lock을 사용하거나, 동시 경쟁을 강제하기 위해 락을 생략한다. 기존 mini_kec DB에 마이그레이션을 실행하지 않았다.

```bash
MINIKEC_MONGO_TEST_URI='mongodb://localhost:27017/?replicaSet=rs0' ./gradlew test --offline --no-daemon
```

동일 요청 재반환, 새 ID 실행, 최초 응답 보존, 진행도 중복 증가 방지, 결과 기록 실패 시 전체 롤백, 락 없는 동일 요청 8건 경쟁, 커밋 후 응답 유실 주입, 요청 범위 분리, API 호환성과 오류 응답을 검증한다.

## 운영 시 고려할 범위

ID 없는 요청과 이미 존재하던 실행 기록에는 소급 적용되지 않는다. 현재 실행 결과에는 만료 시간을 설정하지 않았으며, 이를 삭제하면 삭제된 ID의 재처리 방지 보장도 사라진다.
구버전 서버는 requestId를 처리하지 않으므로 서버가 혼재한 배포 중에는 멱등성을 보장할 수 없다. 전체 서버 업데이트 후 클라이언트에서 이 기능을 사용해야 한다. 구버전으로 롤백해도 저장된 결과는 남지만 구버전이 조회하지 않으므로 재전송 보호는 사라진다.
Redis 보상 카운터 복구와 REWARD 멱등성은 이번 작업에 포함되지 않는다. 인증 주체에 외부 사용자 ID를 연결하는 작업도 별도다.
