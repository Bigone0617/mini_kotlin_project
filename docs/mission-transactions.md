# 미션 완료와 포인트 적립 트랜잭션

## 흐름

User Lock 획득 → 이벤트/반복 정책 사전 검증 → 컬렉션·인덱스 준비 → MongoDB 트랜잭션 실행.
트랜잭션에서는 현재 시각, 최신 UserAction, 반복 정책을 다시 확인한 뒤 진행도/완료 기록과 모든 보상 포인트 적립을 함께 저장한다.
진행 중(PROGRESS)에는 기록만 저장하고, 완료(COMPLETE)일 때만 포인트를 적립한다.

예: 기존 ticket 10, 완료 보상이 ticket +5와 coin +3일 때 coin 적립이 실패하면 완료 기록과 ticket +5도 롤백한다. 이전에 커밋된 진행 기록과 기존 잔액 10은 유지된다. 실패 원인을 해결하고 다시 실행하면 완료와 적립을 함께 커밋한다.

`MongoMissionUnitOfWork`는 기존 MongoDB 트랜잭션 실행기를 재사용한다. TransientTransactionError 재시도마다 최신 상태를 다시 조회한다. 커밋 결과가 불명확하면 전체 작업을 재실행하지 않고 오류를 전달한다.

`earn`의 DuplicateKeyException 처리도 구분한다. 트랜잭션 밖에서는 동시 최초 생성 경쟁을 기존 문서 갱신으로 복구하지만, 트랜잭션 안에서는 오류를 그대로 전달해 전체 롤백에 맡긴다. 실패한 트랜잭션 세션에서 추가 갱신하지 않는다.

## 테스트

```bash
MINIKEC_MONGO_TEST_URI='mongodb://localhost:27017/?replicaSet=rs0' ./gradlew test --offline --no-daemon
```

MissionTransactionTest는 실제 MongoDB의 별도 임시 DB를 사용한다. User Lock은 JVM 락으로 계약만 재현한다. Redis 네트워크나 락 유실 장애 테스트는 아니다.

- 두 번째 적립 실패 시 완료 기록과 첫 번째 적립 롤백, 이후 재실행 성공
- 진행 중 기록이 있는 상태에서 완료 실패 시 기존 진행도 유지
- 적립 후 일시적 오류 시 전체 재시도하며 포인트는 한 번만 반영
- DAILY 같은 UTC 날짜 재실행 거부, 다음 날 실행 허용
- 동일 사용자 8개 요청: NONE 미션 완료 및 적립 1회
- 트랜잭션 내부 중복 키 오류가 원래 오류로 전달되고 모든 변경 롤백

## 범위

보상 자원과 Redis 카운터는 미션 트랜잭션에 포함되지 않는다. 미션 기능에서 사용하지 않기 때문이다.
반복 정책 NONE/DAILY와 정상 User Lock 범위에서 재실행을 제한한다. INFINITE 미션에서 같은 논리적 요청이 재전송되는 것을 구분할 요청 ID/멱등성 기능은 아직 없다.
기존에 이미 발생한 완료 기록/포인트 누락 데이터는 자동 보정하지 않는다. 기존 DB에 수동 마이그레이션을 실행하지 않았다.
